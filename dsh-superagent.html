dsh-superagent: DeepSeek's Proactive GitHub Agent, Reviewed

In one sentence: DeepSeek published dsh-superagent on 2026-10-31 — an MIT-licensed research prototype that turns one GitHub repository into a work queue for an agent: it listens to GitHub (optionally Feishu), opens a Ticket for each authorized request, works in its own session and directory, and answers in the original thread with a pull request. The README states plainly that it is not an official DeepSeek product, and it cannot be installed by package name.

What it is not, in the repository's own words

"Research prototype for reference only, not an official DeepSeek product." The README adds that much of the engineering was done by coding agents, that its style and practices may be inconsistent, and that you should review and adapt it before use. It also notes that some designs discussed in the article are future directions and are not implemented in this prototype.

What happens to one request

The order comes from docs 001 (domain model), 002 (authorization) and 003 (execution). Steps 2 and 3 are the whole point: a message being written is not enough to start work — it has to pass a gate and an assessment.

  1. A Source produces a Trigger — GitHub (notifications, subscribed issues and pull requests, CI changes, merges and closes) or Feishu (live events, history recovery, polling). A Source keeps its own read position, so a restart does not replay events.
  2. The gate checks who is asking — An allowed person addressing the agent directly is an explicit request; a bot on the Source's bot list can only produce an inferred candidate, never an explicit request; other people go through the admission table.
  3. Eval decides — There are exactly four decisions: accept, stop, ignore, unavailable. Only an accept creates a Ticket, and it carries a Mandate that records the Policy version it relied on.
  4. Assignment: one Ticket, one Executor Session, one directory — Executor Sessions are named worker-<ticket id>, with a directory named after the Ticket's short name under the execution root (default <stateDir>/work), created as a worktree from a local clone.
  5. The result goes back to the original conversation — Writes go out through a Channel: Feishu topic replies, GitHub comments, review-thread replies — for example as a pull request. Until a person acts, the result waits in the panel; it does not chase people with messages.
  6. Later discussion needs no second mention — On a thread a Ticket subscribes to, new messages fan out to it as context — including bot and CI messages — but that path bypasses the gate and grants no new authority; the Ticket stays bound by its Mandate.

What you can reuse, and what you must deploy yourself

Doc 001 ends with a reusability table: the concepts and their rules are reusable, while the Source implementations, Policy contents, Executor and Channel implementations belong to a deployment. In practice that means four things to fill in before it works on your repository: Sources, Policy, execution environment and Channels.

Requirements, from the 006 deployment guide

This is not a plugin-sized install: it wants its own profile, its own GitHub account, and a local clone it can add worktrees to.

  • Runtime: Node.js 22.19+ or 24+, pnpm, git 2.32+, Python 3.8+ and tmux.
  • GitHub CLI gh 2.48 or later; the Source CLI fields must point at gh or lark-cli wrappers, whose subcommands and output formats the host relies on.
  • A repository on github.com; GitHub Enterprise Server is not supported. Creating a directory per Ticket needs a local clone for the prepare command to add worktrees; install git-lfs if the repository uses Git LFS.
  • A dedicated GitHub user account for the agent with write access to the repository. A GitHub App cannot be the agent, because dsh-superagent reads the account's notifications.
  • A model provider already configured for DeepSeek Harness; it uses the profile's default model unless the Eval or Execution settings name another.
  • Feishu is optional: it needs lark-cli (tested at 1.0.90 according to the guide) and a Feishu or Lark app with a bot.
  • Version note: package.json declares engines.dsh as ^0.2.1-alpha.2; the one-time block in 006 installs @deepseek-ai/dsh@0.2.1-rc.3 and says other versions must satisfy engines.dsh.

Two ways in

The official route is either to let a coding agent walk you through it (recommended) or to run the block from 006 yourself. The commands below are copied from 006 and the repository root, with nothing added.

  1. Route one: let an agent do it — The README's instruction is to ask your coding agent to read SETUP.md and set it up with you. It asks one short question at a time (Feishu or not, which repository, which account, who may ask for work), shows the full plan once, and installs only after you confirm.
  2. Route two: the manual block 
    npm install -g @deepseek-ai/dsh@0.2.1-rc.3
git clone <this repository> dsh-superagent && cd dsh-superagent
pnpm install && pnpm build
dsh superagent --from-default-profile web --dump-config > /dev/null
dsh plugin --profile superagent add "link:$PWD"
  3. The steps only the operator can do — Create the agent account, accept the repository invitation, run auth login for each wrapper, and on the Feishu side create and publish the bot app and run config init. Afterwards, check each login with <wrapper> api user --jq .login.
  4. First test: mention it in an issue — From an account on the allowed list, comment @<agent login> <request> on an issue in the repository; a Ticket appears on the overview within about a minute.

Limits the documentation states itself

This page does not decide for you whether to run it; it only pulls out the lines in the official docs that get skipped but do matter.

The permission model is "an OS user just like you"

  • Both presets — dsh-superagent-worker for Executors, dsh-superagent-router for the main Session — run with danger-full-access as the operator's OS user.
  • The guide says outright that a worker can execute programs by path and read the operator's home directory, and that account wrappers only choose credentials — they do not isolate the process. For isolation, use a dedicated OS account holding only the agent's credentials.
  • The bundle changes process-wide PATH and git settings, which is why the guide insists on a dedicated profile (superagent) rather than the one you work in.
  • Both presets appear in the DeepSeek Harness preset list, but the guide says not to select them for personal Sessions or disable their configuration rows: the application needs them to create and resume its Sessions.
  • It saves attention by staying quiet, but the quality of its judgement is set by the Policy you write: the advice is to start with a short allowed list and with proactive work only recorded, then widen once what it would have done looks right.

FAQ

Is it an official DeepSeek product?

No. The first line of the README is "Research prototype for reference only, not an official DeepSeek product." It grew out of the team's day-to-day work with much of the engineering done by coding agents, and the repository asks you to treat it as research code.

Can I install it as a package name, like a plugin?

No. package.json is private: true at version 0.1.0. Doc 006 clones locally, runs pnpm install && pnpm build, then dsh plugin --profile superagent add "link:$PWD" into a dedicated profile created from the Web template.

Do I have to wire up Feishu?

No. The README says it listens to GitHub and, optionally, Feishu. With GitHub only, limit Sources to GitHub; Feishu additionally needs lark-cli (documented at 1.0.90) and a Feishu app with a bot.

Will it act when nobody asked?

Only where a rule the team wrote allows it, and that kind of work starts in a mode that only records what the agent would have done. The stated discipline is that it acts only when asked or when a written rule allows it, and a bot can only produce an inferred candidate, never an explicit request.

What does it cost to run?

The repository publishes no pricing or token budget; it says only that it uses the profile's default model unless the Eval or Execution settings name another. Cost therefore depends on your own model configuration and on how wide your Policy is — more allowed work means more spend.

How does it relate to the Exploring Super-agent Design article?

It is the public prototype of that design, but the README says explicitly that the code was adapted for publication and is not identical to the internal version or to the implementation the article describes; some designs in the article are future directions that this prototype does not implement.
